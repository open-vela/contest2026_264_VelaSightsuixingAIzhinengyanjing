## 五、发现的问题一：`nuttx` pin baseline 在上游已丢失

### 现象

执行只读校验：

```bash
cd contest2026_264_VelaSightsuixingAIzhinengyanjing
sh external/prepare.sh check \
  --openvela-root ~/vela_competition/contest \
  --bk-avdk-root ~/vela_competition/bk_avdk_smp
```

报错：

```text
prepare.sh: error: nuttx baseline commit is unavailable: 4a67a7bad6bba672db2ac37a64acbdc3c024d6e5; fetch https://github.com/open-vela/nuttx.git
```

### 排查过程

`external/manifest.tsv` 中 `nuttx` 行 pin 的 baseline commit 是：

```text
4a67a7bad6bba672db2ac37a64acbdc3c024d6e5
```

依次验证该 commit 是否存在于上游 `open-vela/nuttx`：

1. `git -C nuttx cat-file -e 4a67a7bad6bba672db2ac37a64acbdc3c024d6e5^{commit}` → `Not a valid object name`（本地不存在，符合预期，因为 `repo sync` 默认只拉取分支尖端附近历史）。
2. `git fetch openvela 4a67a7bad6bba672db2ac37a64acbdc3c024d6e5` → `remote error: upload-pack: not our ref`（服务端明确表示这不是一个可达的 ref/object，而不是"本地缺历史"）。
3. GitHub REST API `GET /repos/open-vela/nuttx/commits/4a67a7b...` → `422 No commit found for SHA`。
4. GitHub 全局 commit 搜索（cloak-preview）→ `total_count: 0`。
5. `git ls-remote https://github.com/open-vela/nuttx.git` 返回该仓库全部 377 个 refs，其中包含一条 `refs/heads/dev-ai-contest-2026-backup-before-override-20260526`（分支名暗示上游曾对 `dev-ai-contest-2026` 做过一次历史覆盖/重写）；将该备份分支也 fetch 到本地后，pin commit 依然不在其历史中。

结论：**这个 commit 对象在 `open-vela/nuttx` 仓库的当前状态和已知备份分支中都不存在**，与本地 sync 深度无关，是上游仓库自身的历史丢失（大概率是一次 force-push/历史重写导致该提交连同其祖先被丢弃），不是本地操作问题。

`apps` 和 `packages/ai_agent` 的 pin commit 校验完全正常（HEAD 恰好等于 pin 值），说明问题只出在 `nuttx` 这一行。

`external/prepare.sh` 对四个仓库是整体校验、整体放行的：只要有一行 baseline 不可解析，就会拒绝安装全部 56 个受管文件（包括其余三个仓库本来健康的部分）。

### 处理方式

`nuttx` 工作树是刚 `repo sync` 出来的干净副本（`git status --short` 无任何输出），不存在需要保护的本地修改。`prepare.sh` 里 baseline 字段的作用是"确认目标仓没有未知本地改动"，在没有本地改动的前提下，把 baseline 改成实际同步到的 HEAD 是等价的安全操作，不会绕过任何真实的完整性检查。

本次处理：仅在本地工作副本的 `external/manifest.tsv` 中，把 `nuttx` 行的 baseline 由 `4a67a7bad6bba672db2ac37a64acbdc3c024d6e5` 改为实际同步到的 HEAD：

```text
dd92bcf425738734d1b8aed09c2bd4dbe3f2e438   ("drivers/lcd/lcd_dev: Add poll support")
```

**这一改动只停留在本次复现使用的本地工作副本里，没有提交、没有推送。** 是否需要把这个修正提交进团队仓库（并同步更新其他协作者的 pin 值），留给仓库维护者决定，见第十一节的建议。

## 十、发现的问题二：`bk_loader` 烧录工具不在仓库管理范围内

### 现象

构建完成后准备执行 `./autoflash.sh`，但 `autoflash.sh` 的 `find_root()` 逻辑要求在工作区根找到可执行的 `bk_loader` 或 `tools/bk_loader`，而这个二进制既不在团队仓库里，也不在 `external/manifest.tsv` 管理的四个仓库（`apps`/`nuttx`/`packages_ai_agent`/`bk_avdk_smp`）里，也不在 Armino Docker 镜像内。

`docs/archive/BK7258_bk_loader_Linux烧录教程.md` 提到该工具版本 `2.1.11.8`，但只说明"放在一个方便的目录"，未给出获取地址。经查，`bk_loader` 是 Beken 官方 BKFIL（Beken Flash Image Loader）配套的命令行程序，属于厂商专有工具，不通过开源仓库分发，`dl.bekencorp.com` 官网也有人机验证网关，无法用脚本直接抓取。

### 处理方式

**Linux 版 BKFIL（含 `bk_loader`）官方下载地址：**

```text
https://dl.bekencorp.com/tools/flash/Linux-BKFIL
```

从该地址获取后放入工作区根目录（与团队仓库、`bk_avdk_smp` 同级），并赋予执行权限：

```bash
chmod +x ~/vela_competition/bk_loader
~/vela_competition/bk_loader --version
```

```text
bk_loader version 2.1.11.8: build @May  8 2024 23:15:55
```

版本号与 `docs/archive/BK7258_bk_loader_Linux烧录教程.md` 中记录的验证版本一致。`autoflash.sh` 的 `find_root()` 从团队仓库位置向上逐级查找，能正确定位到工作区根的这个 `bk_loader`。

> 建议：`docs/archive/BK7258_bk_loader_Linux烧录教程.md` 和 `README.md` 第 4.1 节都没有说明 `bk_loader` 的获取地址，属于文档缺口。建议后续把上面这条官方下载地址补充进 `external/README.md` 或 `docs/archive/BK7258_bk_loader_Linux烧录教程.md`，避免下一个从零复现的人在这一步卡住。
